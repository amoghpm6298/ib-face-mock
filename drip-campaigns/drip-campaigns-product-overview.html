Drip Campaigns

A visual way to build multi-step customer journeys.

Drip Campaigns is a builder for setting up how a bank or issuer talks to its customers over time. A campaign is a sequence of communications, waits, and decisions, not one message sent once.

A campaign starts by defining who can enter and what counts as success. Then it lays out a journey on a canvas. The journey is a chain of steps. Each step can send a message, wait, branch customers down different paths, or check whether they've reached the goal.

Section B

How a campaign works

A campaign is built in five steps. Steps 1, 2, and 4 define the campaign as a whole. Step 3, the Builder, is where you lay out the journey.

Campaign-level configuration
1
Basic Details

Name, description, issuer & program scope, control group %, re-entry rule, schedule.

2
Goal

The event, and any conditions, that count as success.

Journey-level configuration
3
Builder

Define entry. Add nodes to the canvas and connect them. Configure each node's conditions, communication settings, or timing.

Campaign-level configuration, continued
4
Guardrails

Exclusion lists: Do Not Contact and Non-Performing Assets. Checked at every step, not just at entry.

5
Review

A read-back of everything above, then Save as Draft or Submit for Approval.

Outcomes live inside the journey, not as a separate step. Every path through the canvas ends at Goal Reached or Exit. Goal Reached means the customer achieved the goal. Exit means the journey ended without it.

Section D

Node reference

What each node accepts as configuration, and what it produces: which customers continue, and down which path.

Entry · Audience

Entry

Root node. One per campaign.

Qualifies a customer based on their current attributes. Re-checked on a schedule if the audience repeats.

Configuration

FieldTypeValues / default
entityselectCustomer · Account · Card · Transaction · Milestone — default Customer
conditions[]arrayattribute + operator + value rows, scoped to the chosen entity. Unused when entity is Milestone.
milestoneobjectonly shown when entity = Milestone — which benefit, which condition, and what value. See Condition for the full shape.
lookbackDuration + lookbackUnit + existencenumber + select + selectonly meaningful (and only shown) when entity = Transaction — days/hours lookback window, default 90/days, and whether a matching transaction must exist or must not, default exists
extraEntityGroups[]arrayzero or more extra entity filters, same shape as the primary block above, each AND'd with it. Default []. Lets one audience combine entities, like Account = Dormant and Card = Active, or even two different Transaction checks.
repeatbooleandefault false
recurrenceTypeselectMonthly · Weekly · Daily — only shown if repeat is true, default Monthly
timeOfDaytimedefault '09:00'

Output

Starting segmentEvery customer who matches the primary block and every extra entity filter. This is where the rest of the journey starts from.

This is an entry-time check only. It decides who qualifies to start. What happens after that is up to the nodes that follow.

Transaction is a real entity choice, not a separate toggle — picking it reveals a Lookback and Match field under the usual Filters, since its attributes already exist and render the same way every other entity's do.

Milestone is a real entity choice too. It checks whether a customer has completed, or not completed, a specific benefit, like a spend target. This is the main way a Promotional campaign's whole audience is qualified, not just an extra filter.

"+ Add another entity filter" adds one more entity block, each independently removable. A customer must match every block.

Entry · Event

Entry

Root node. One per campaign.

Qualifies a customer the moment they fire a specific event.

Configuration

FieldTypeValues / default
eventCategoryselectsee Event categories — default Journey Events
eventTypeselectdepends on eventCategory, see Event categories — required
journey / batchselect + selectonly for Journey Events — optional, blank by default
offerType / offerNameselect + textonly for Offer Events — optional, blank by default. offerName is free text, since there's no real catalog of offer names to pick from.
conditions[]arrayTransaction/EMI Events narrow by a real attribute (Transaction or EMI Request). Journey/Offer Events narrow by one fixed attribute per event type instead (e.g. Pageload locks to "Page Name"). Card Events has neither.

Output

Starting segmentEvery customer who fires the event and matches the configured conditions, if any.

Send

Actions

Sends a communication to the customers who reach this step.

Configuration

FieldTypeValues / default
nametextstep name, default 'Send Message'
channelselectsee Channels — default WHATSAPP
accountselectdepends on channel — required
templateIdselectdepends on channel + account — required
timingselectAbsolute · Relative — default Absolute
absTimetimeonly if timing = Absolute, default '11:00'
relativeDuration + relativeUnitnumber + selectonly if timing = Relative — delay after the previous step, default 1 / days. 0 reads as "Immediately after previous step."
fallbackChannelselect'' (no fallback) or any channel except the primary — default ''. See Channel Failover below.
fallbackAccount + fallbackTemplateIdselect + selectonly if fallbackChannel is set

Output

Unchanged segmentA Send doesn't filter anyone out. Everyone who reached it carries forward, whether delivery succeeded or not.
Auto-fork, if a Goal is definedThe outgoing segment is split right away by an automatically inserted Goal Check. See Goal Check.

The delivery status, like delivered or bounced, feeds downstream Condition and Branch nodes through the "Previous step outcome" source.

Parallel paths

A way to connect steps, not a separate node

Lets one step lead to several next steps at the same time. Everyone who reaches that step goes down every path.

This is different from Condition, Branch and Experiment. Those send each customer down only one path. Parallel paths send everyone down all of them.

When you would use it

Checkpoints from one startA campaign that checks on a customer at several fixed points in time. Spend Milestone checks at Month 1, 3, 6 and 12, all counted from the day the card was activated. Anniversary programmes and onboarding check-ins work the same way.

How to use it

Add a pathHover over a step that already has a next step. A "+ Parallel path" link appears. Click it and pick the step you want, same as usual.
Name each pathOnce a step has more than one path, each path shows a "+ Name" prompt on its line. Click it and type a name, like "Month 1". This only appears where there is more than one path, since a single line needs no name.

Not available on Condition, Branch, Experiment, Goal Check or Wait for Event. Those already split into several paths, and their path names are set in their own panel.

Four paths fit comfortably on screen. Beyond about six the canvas gets wide and you will need to zoom out or scroll.

Channel Failover

Part of Send, not a separate node

A fallback channel, account, and template, configured directly inside a Send step. Used when the primary channel's delivery fails for a customer.

Configuration

FieldTypeValues / default
fallbackChannelselectany channel other than the primary — default '' (no fallback)
fallbackAccount + fallbackTemplateIdselect + selectrequired once fallbackChannel is set — same dependency rules as the primary pair

Output

Same Send, one of two channelsThe journey continues exactly as a normal Send would. Downstream "Previous step outcome" conditions account for either channel delivering.

There is no separate "Channel Failover" step to add to the canvas. This capability lives entirely inside Send's own configuration panel.

Wait

Wait

Pauses the journey for a fixed amount of time.

Configuration

FieldTypeValues / default
durationnumberdefault 2
unitselectdays · hours — default days

Output

Unchanged segmentNobody is filtered out. The same customers continue once the wait elapses.
Auto-fork, if a Goal is definedSame rule as Send. Split by an automatically inserted Goal Check.

Wait for Event

Wait

Pauses until a specific event happens, or until a timeout is reached, whichever comes first.

Configuration

FieldTypeValues / default
eventCategoryselectsee Event categories
eventTypeselectdepends on eventCategory — required
journey / batch / offerType / offerName— / —same optional scoping fields as Entry · Event, shown under the same conditions
duration + unitnumber + selecttimeout — default 7 / days
conditions[]arrayresolved the same way as Entry · Event

Output — splits into two

YesThe event occurred before the timeout.
NoThe timeout was reached without the event occurring.

If the event carries a status attribute that matches the campaign Goal, Yes is wired straight into a real Goal Check. That Goal Check's Yes goes to Goal Reached, and its No goes to an auto Exit labelled "Resolved, but not to the goal outcome." Otherwise, both paths are left open for you to configure.

Condition

Decisions

Evaluates a configured condition and forks the journey into two paths.

Configuration

FieldTypeValues / default
customSourceselectPrevious step outcome · Account attribute · Entry event attribute · Transaction history · Milestone — default Previous step outcome. To fork on the campaign Goal, use the Goal Check step instead.
outcomes[]multiSelectonly if source = Previous step outcome — a set of delivery statuses from the last Send; any one match → Yes
customConditions[]arrayonly if source = Account attribute or Entry event attribute — ALL must match → Yes. For a Journey/Offer Events entry, this becomes one fixed-attribute condition instead of a free attribute pick.
txnHistoryobjectonly if source = Transaction history — filters + lookback duration/unit + existence mode (exists/none)
milestoneobjectonly if source = Milestone — which benefit, which condition (Completed/Not Completed, or a number/percentage comparison), and the value to check

Output — splits into two

YesThe condition matched. For Transaction history, it means the check matched. For Milestone, it means the benefit's progress matched.
NoThe condition didn't match.

A single simple condition shows a readable summary on the canvas, like "Status = Active?" or "Spend ₹75,000 in first 90 days — Completed?". Two or more conditions, or a complex one, collapse to "Custom condition" plus a count. Raw operators and values are never shown on the canvas.

Branch

Decisions

Routes customers across several named paths, based on one attribute or the previous step's outcome.

Configuration

FieldTypeValues / default
nametextstep name, default 'Decision'
sourceselectPrevious step outcome · Account attribute · Entry event attribute · Milestone — default Account attribute. No "Goal" source — a binary goal doesn't map onto an N-way branch.
attributeselectrequired for Account attribute or Entry event attribute. For a Journey/Offer Events entry, fixed to that event type's one locked attribute instead of a free pick. Changing it clears every branch's value, since a different attribute can be a different value type.
milestoneBenefitIdselectrequired for the Milestone source — the one benefit every branch below is compared against
branches[]array{label, operator, value, value2, values?} — default 2 branches. For Milestone, each branch can use a different condition (like under 25%, between 25 and 75, or Completed), all against the same benefit — a natural way to route by progress tier.

Output — splits into N groups + a catch-all

One group per branchCustomers are sorted into whichever branch they match first, checked top to bottom.
Catch-allImplicit, and always last. Customers who match none of the configured branches land here.

Experiment

Experimentation

Randomly allocates customers across variants by percentage. It isn't based on anything about the customer.

Configuration

FieldTypeValues / default
nametextstep name, default 'Channel test'
branches[]array{label, pct} — default 2 branches, A/B at 50% / 50%

Output — splits into N groups by chance

One group per variantAssigned randomly according to the configured percentages.

Validation: variant percentages must sum to exactly 100.

Goal Check

Decisions

Added automatically, or by hand.

Evaluates the campaign-level Goal at this point in the journey.

How it gets added

AutomaticallyOne is placed after every Send and every Wait, as soon as a campaign Goal is set. You don't have to do anything.
By handPick it from the Add Step list to check the Goal anywhere else — after a Wait for Event, or on a Branch, Experiment or Condition path, where no automatic one appears. It stays greyed out until a Goal is set, since there would be nothing to check.

Both routes build exactly the same step, wired the same way. Condition used to carry a "Goal" source that asked the same question but left both paths open, so one question could produce two different journeys. That source is gone.

Configuration

None. It carries no configuration of its own. Its question always comes from the campaign's current Goal, so editing the Goal after the journey is built updates every existing Goal Check automatically.

Output — splits into two

YesThe customer achieved the Goal. Routed to Goal Reached.
NoNot yet. The journey continues.

This app has no execution engine. Nothing here is actually evaluated in real time.

Goal Reached

Outcomes

Terminal node.

Means the customer achieved the campaign Goal.

Configuration

FieldTypeValues / default
reasontextauto-filled from the campaign Goal's label, or 'Goal achieved' if there's no Goal. Editable, but set once. It won't update if you edit the Goal later.

Output

TerminalThe journey ends here for this group of customers, counted as converted.

Different from Goal Check. Goal Check is the evaluation. Goal Reached is where customers land once the answer is Yes.

Exit

Outcomes

Terminal node.

Ends the journey for customers who didn't achieve the Goal.

Configuration

FieldTypeValues / default
reasontextdefault 'Sequence exhausted'

Output

TerminalThe journey ends here for this group of customers, not counted as converted.

Different from Goal Reached. The journey simply ran out of steps instead of reaching the goal.

Section F

Campaign setup and management

Beyond the journey itself, a campaign carries its own setup and lifecycle.

1
Basic Details

Name, description, issuer and program scope, control group held back for measurement, re-entry rule, schedule.

2
Goal

The event that counts as success for this campaign.

3
Builder

The journey canvas. Entry, nodes, and connections.

4
Guardrails

Exclusion lists, on by default. Checked at every step.

5
Review

Full read-back, then Save as Draft or Submit for Approval.

Campaign lifecycle

Draft Pending Approval Revision Required Active Scheduled Paused Killed

The campaign listing shows these statuses alongside issuer, program, entry type, and whether a Goal is set. A team can see at a glance what exists, what's awaiting approval, and what's live.

Section G

Important product concepts

The core vocabulary a stakeholder needs to read a journey correctly.

Entry criteriaThe attributes or event that determine which customers qualify to enter a journey.
ConditionEvaluates a configured criterion and produces a Yes/No fork.
BranchRoutes customers across several named paths based on one attribute or outcome.
ExperimentAllocates customers to variants at random, by percentage.
Campaign GoalThe customer outcome that defines success for the whole campaign.
Goal CheckEvaluates the campaign Goal at a point in the journey. Added automatically after every Send and Wait; you can also add one yourself anywhere else.
Goal ReachedA terminal state that means the customer achieved the Goal.
ExitA terminal state that ends the journey without reaching the Goal.
