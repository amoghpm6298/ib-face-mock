Campaign Designer

A campaign manager describes a business outcome in plain language. The agent establishes what it needs to know first, works out where in the customer's sequence an intervention belongs, then recommends a strategy with its trade-offs and builds the journey using the Drip Campaign platform's own graph engine. Discovery finishes before a design appears. Once it has, any question still open arrives next to the recommendation rather than instead of it.

01

What the agent does

Building a drip campaign today means knowing the platform. You need the right entry event, the right status values, a goal definition, channels, timing, branching and exit rules. The Campaign Designer removes that requirement. You describe the outcome you want. The agent works out the rest, and asks you only about things it genuinely cannot look up.

It behaves like a strategist rather than a form. It reads the platform's own capabilities — including the exact values each field accepts, and it does that before asking you anything. It reasons about where in the customer's sequence an intervention belongs, rather than matching your wording to an event name. And it recommends rather than handing you a list of options: anything still open arrives next to the recommendation, not in place of it.

Understands the objective

Takes a business outcome in chat. It separates that outcome from the formal goal the platform needs.

Investigates before asking

Checks real event types, audience attributes, channels and step types using live tool calls.

Asks what matters

The agent decides what to ask and how to word it. Only what would change the design reaches you, alongside the recommendation.

Requests useful evidence

Asks for specific aggregates when they would settle a real decision. Declining is always a valid answer.

Recommends a strategy

Explains the approach, the rejected alternatives and the assumptions. It makes no claims about lift.

Writes the messages

Drafts copy addressed to the customer, with a call to action, and keeps it on the step for you to work from.

Builds the real campaign

Constructs the journey with the platform's own reducer, then validates it with the platform's validators.

02

The end-to-end workflow

The flow has three hard rules. Discovery finishes before a strategy reaches you. The agent states the intervention it wants before it is told what the builder can express, so a requirement you asked for cannot quietly become whatever happened to be buildable. And no campaign is built until you confirm that strategy. All three are enforced in the application, and the canvas stays empty until you say yes.

The confirmation gate

Graph construction is reachable from one place only. The application records your confirmation against the current objective and the current strategy version. If either changes afterwards, that confirmation no longer applies and the agent returns to the strategy.

03

How the agent designs a campaign

The agent follows a method rather than filling in a form. It goes deeper where the objective needs it, skips what it does not, and says which parts it skipped. For every real decision it states the decision, what it relied on, and the trade-off it accepted.

StepWhat it settles
Outcome and behaviourWhat the customer must do differently, named as an action rather than a metric. Then how success would be judged, in the business's own terms.
Who converts, and why the rest do notTwo findings the agent must get from you. The first is who converts today. The second is what stops everyone else. Neither can be invented, and the agent cannot propose a campaign without both.
The dimensionsThe three to five things about this objective whose answers could change the campaign. Settled before an entry event is chosen.
The sequenceWhat happens to the customer in order, and where an intervention can still change it.
The hypothesisBy what mechanism the messages should change the behaviour. A hypothesis, never a prediction.
The journeyThe simplest sequence that does the job. There is no per-campaign message cap. That cap was invented data, and it was removed once we recognised that banks do not set one uniform limit for every campaign.
The messagesCopy written to the customer, with a real call to action.
What is settledWhich facts you confirmed, which the agent assumed, and what is still open.

Choosing where the campaign starts

This is the step that most often goes wrong, and the one the method exists for. Several events can mention the same subject while sitting at different points in a customer's sequence. The agent is required to reason about that order rather than match the objective's wording to an event name.

The same subject, two different campaigns

Asked to convert an authorised purchase, the campaign should begin at the authorisation, because the customer has not raised a request yet. Asked to rescue requests already sitting unfinished, it should begin at the request, because they have. Same subject, different point in the sequence, different correct answer. An agent that matches on the word alone gets one of the two wrong.

04

How discovery works

A one-line objective is not a campaign brief, so the agent has to find out what it does not know before it designs anything. Discovery coming first is a property of the application, not a request in a prompt: a strategy offered before the investigation is finished is refused, and what the agent wrote is discarded rather than shown.

Worth being precise about what that does and does not guarantee. You will not be shown a design before discovery is finished. It does not force the agent to open with a question: the agent is told to discover first, and when it tries to design too early instead, your first reply is a short note saying discovery continues, together with what it is working through. That is the application correcting the agent, and it reads differently from the agent simply asking you something.

The opening round is reserved for one thing: what the business would count as this working. That is sequencing rather than etiquette. A count of conversions and a value of conversions pull in opposite directions and produce different campaigns, and the answer decides which of the remaining questions are worth asking at all. Asked in the same breath as the audience and the cause, it arrives too late to direct them.

A factor the agent raises is then its own to resolve. It can ask you, check the platform, or proceed on an assumption it states. What it cannot do is name something that could change the campaign, leave it uninvestigated, and design around it anyway. Setting a factor aside is a decision the agent has to make out loud, which is the difference between a judgement and an omission.

Five things have to be true before a strategy is accepted. You have taken part at least once, so the agent cannot answer its own questions. Success has been defined, even if the definition is “no target yet, so this is the working measure”. The agent knows who converts today. It knows at least one real reason the rest do not. And nothing it raised itself is still open. None of these is a round count. A clear brief resolves them quickly. A vague one takes longer.

What the agent investigates

The agent names the three to five things about this objective whose answers could change the campaign, and records what became of each. It does this before choosing an entry event, because choosing the trigger first tends to turn every remaining question into a platform question. A dimension is raised first and classified second: one that matters but cannot be built is kept and reported, never dropped for being inconvenient.

StatusWhat it means
OpenStill being investigated. A strategy is not accepted while anything is open.
RetainedResolved, and used in the design.
DeferredCould matter, deliberately not pursued now, with the reason recorded. A decision, not an omission.
UnavailableThe platform cannot express it at all. Reported as a limitation rather than quietly abandoned.

Each one also records what its status rests on: a tool result, something you said, an explicit assumption, or nothing yet. The distinction is enforced, not decorative. A dimension closed on an assumption cannot be stored as an investigated finding, and a limitation claimed on an assumption cannot be stored as a verified one — both are rewritten as deferred, keeping the agent's reason and marking the limitation unverified.

Why an assumption is not a finding

“We checked and it is not there” and “we assumed it is not there” must never read the same way. The first closes a question; the second is a decision to proceed without evidence. Claiming the platform cannot do something without checking is the more costly of the two mistakes, because it removes a strategy that may have been perfectly buildable.

How remaining points are classified

Strategic ambiguity

A business definition only you can settle, such as which status value means a request converted. It is put to you as a question, next to the strategy rather than instead of it.

Evidence gap

An aggregate that would sharpen a decision. Never a prerequisite. If you do not have it, the agent proceeds and records the limitation.

Optional preference

A detail with a sensible default, such as send time. The agent states the default it applied instead of asking you to choose.

Operational limitation

Something the platform cannot confirm either way, such as a Smart Tag value it has no list for. Stated, not quietly assumed.

Who writes the questions

The agent does. It decides what it does not know, how important that is, and how to word it, and you see its wording. The application's job is narrower: it drops anything you have already answered, it shows only the points the agent marked as genuinely strategic, and it caps a round at three so a design conversation cannot turn into an interview.

There is one exception, and it is deliberate. When you state a value the platform cannot represent, the application raises that itself, because it is the only party that knows the real alternatives. That question is written from platform metadata rather than by the agent, and it names the values you can actually use.

Once discovery is done, the strategy is never withheld

These two rules sound opposed and are not. While the investigation is unfinished there is nothing to recommend yet, so the agent keeps asking. Once it is finished, an honest open question never costs you the design: the recommendation and the question arrive together, which an earlier version got wrong by returning a question instead of the campaign you asked for.

The working brief

Everything established during discovery is kept in a working brief. It is sent back to the agent on every turn, which is what stops it repeating a question or contradicting an earlier answer.

Held in the briefWhy it is kept
Original objectiveKept even when you clarify it. Clarifying withdraws the approval, it does not erase the brief.
Success criteriaHow the business would judge the campaign. Required before a strategy is accepted.
The dimensionsWhat was investigated, what became of each, and what that rests on.
Questions and answersNothing already answered is asked again.
Established factsEach one is tagged with where it came from.
Evidence requestsMarked as pending, supplied or unavailable.
LimitationsMissing evidence is carried into the strategy honestly.
Values you statedChecked against platform metadata, and kept in your own words.
Unresolved conflictsA value the platform cannot hold is raised, never quietly swapped.
Discovery ends on resolution, with a ceiling behind it

Discovery finishes when the material questions are resolved or explicitly handled — not after a set number of exchanges. Behind that sits a ceiling: a round asks at most three questions, and discovery runs for at most eight rounds. You can ask the agent to proceed at any point, and both the ceiling and your request override everything above; whatever is still unknown is then carried into the strategy as a stated assumption or an open unknown rather than dropped.

What a strategy contains

The strategy is a read-back of the whole investigation, not just a journey. Sections appear only when the agent has something to put in them.

SectionWhat it holds
Summary and approachThe design and the reason for each decision.
Considered and not usedWhat was rejected, and why. Often the most useful part.
Success criteriaHow the business would judge this campaign, in its own terms.
MeasurementWhat to track, how to evaluate it, and what would be needed to measure it properly. It is qualitative only. There is no target, no history and no forecast, because no performance data exists.
AssumptionsWhat the agent proceeded on without confirmation.
Hypotheses for future testingWorth investigating later. Explicitly not claimed now.
Worth settling, and defaults appliedOpen questions with the default the agent used until you answer.

05

The two findings the agent has to come back with

A campaign to raise conversion needs two things that no system here can look up. The first is who converts today. The second is what stops everyone else. The agent has to get both from the conversation. It cannot design a campaign until it has them.

This was added because the agent kept designing the wrong thing. Across thirty-five recorded runs it never once asked either question. It asked instead about KYC completeness, suppression lists and account standing. That is not a failure of tone. Those were the only kind of question available to it. Everything the agent is given is operational. It has a list of fields it can filter on, a list of rules it must not break, and a description of how the builder works. None of the eleven campaign principles says anything about why a customer converts. The knowledge base states plainly that no performance history exists. Asked to raise conversion with only that to go on, audience plumbing is the only thing it can reason about.

Nothing is pre-loaded, and that is the mechanism

An earlier version of this shipped a list of five likely reasons customers do not convert. That was wrong and it was removed. A ready-made list turns the conversation into multiple choice. The agent stops listening and starts matching what you said to the nearest item on the list. It also caps the answer at whatever the list's author happened to think of. A real reason outside the list gets forced into the closest available box. Working out the reason is the job. An empty slot that must be filled is what forces the question. A pre-filled one removes the task.

RuleHow it is enforced
A reason must trace to something you actually saidThe agent has to quote you. The application checks that quote against your real replies. If it does not match, the reason is recorded as the agent's own assumption, and no campaign may be built on it.
Paraphrasing is allowedThe check compares meaningful words rather than demanding an exact quote. A model repeating a conversation drops filler and fixes grammar. Demanding a literal match would reject honest attributions more often than dishonest ones.
Every message names the reason it attacksChecked against the built journey. A message that attacks nothing is not a message. It is another contact.
Every reason you raised must be attacked by somethingAlso checked against the journey. This is the worse failure of the two. You raised it, and the campaign quietly did nothing about it.
“Nothing can fix this” is a real answerThe agent can mark a reason as one a drip campaign cannot address. That is a legitimate finding. It previously had no way to say it.

When nobody knows who converts

A fresh campaign has nobody who has converted yet. A running one may have converters without anyone knowing who they are. This is the case where the agent has to work hardest, so it is the case the rules are strictest about.

SituationWhat the campaign has to do
You can describe who convertsTwo strategies are worth comparing. Double down on that profile, or go after everyone else. The agent builds both and says which it chose and why.
Nobody has converted yetThere is nothing to double down on, so the campaign's job changes. It has to find out who converts.
Conversions happen but nobody knows whoThe same. The campaign has to find out.

In the last two cases the agent cannot accept “we have no data” and move on. That used to be allowed. It meant the one situation needing the most thought was the one the agent was permitted to skip. It now has to put forward at least two candidate segments, each with its reasoning, and ask which you would back. One candidate is a guess. Two or more is something you can argue with or rule out. It then has to wait for your reply before designing around any of them. An agent that proposes a target and treats its own suggestion as agreed is the easiest mistake to make here.

The design itself is checked too. A journey that treats everyone the same cannot learn who converts. The result would be one undifferentiated number, and the next campaign would start as ignorant as this one. So the campaign has to separate the candidate segments. It can use a test that compares audiences, or a branch that treats them differently.

06

How the prompt is built

The agent is driven by one instruction document of about thirty-three thousand characters. It is worth understanding how that document is organised, because its shape decides what the agent can think about.

Roughly half of it is the design method, written as nine numbered steps in a deliberate order. About a quarter is the exact shape of the answers the agent is allowed to return. The rest is ground rules.

Part of the promptShareWhat it does
The design methodabout halfNine steps in sequence, from the outcome through to the messages. The order is the point. Settling the objective before the audience, and the audience before the platform, is what stops the platform deciding the strategy.
The answer shapesabout a quarterThe exact JSON the agent may reply with. There is one shape for asking questions, one for stating the intervention, and one for proposing a campaign.
Ground rulesa small partWhat it must never claim. It also states that the agent is writing to a campaign manager and not to an engineer.
The step vocabularya small partEvery kind of step the agent may design with. Widening this list is the single change that has most improved the output.

The length limit is a test, not a guideline

A test fails the build if the prompt grows past its limit. A second test fails the build if the method section shrinks below forty per cent of the whole. Together they stop the prompt filling up with rules while the method itself gets squeezed. The limit has been raised deliberately and rarely, and only for new capability. Adding the two findings and teaching the agent that entry can combine several entities was one such time.

The schema matters more than the wording

The clearest lesson from building this is that the shape of what the agent is asked for changes what it thinks about, and the wording mostly does not. One example makes the point better than the general claim. The agent used to state its intervention as a list of needs. Each need sat next to “the attribute that expresses it” and “the event it could wait for”. That shape only comfortably accepts needs that have an attribute. A real requirement such as “they think it is expensive, so the first message has to reframe the cost” has neither, so the schema quietly pushed it out. Three of the four requirements the agent stated came back as audience plumbing. Nothing in the wording asked for that. The slots did.

Three rounds of rules changed nothing

Guards, required contingencies and feedback loops were added over three rounds. They made the agent more honest about what it did not know. They did not change what it designed. Two changes did move the output. Widening the list of steps it could design with took a campaign from two messages to ten and produced the first real branch. Making the application refuse an experiment whose arms were identical stopped it claiming tests it had not built. Both are structural. Neither is a sentence in the prompt.

07

The model and application boundary

There is a step between asking and building that is easy to miss and does most of the work. The agent states the intervention on its own first. That means who it wants to reach, at what moment, and what the journey has to do. It states all of that before it is told what the builder can express. Only then does the application answer, from the platform's real metadata, which of those requirements can be met where the campaign starts, which would need a different starting point, which the journey can wait for instead, and which nothing supports at all.

The ordering is the point. The agent reads the platform's vocabulary during discovery, so an agent asked for an intervention and a campaign in one breath describes an intervention that happens to match what it could already build. A requirement you asked for disappears with nobody deciding to drop it. Stating the intervention first makes that gap the application's finding rather than the agent's prose, and it arrives in front of you as a cost you can weigh.

The model does business reasoning. The application does everything structural, and it checks the model's work rather than trusting it. The model never gets to invent a node type, an event, a field name, an identifier — or a value. Every condition is validated against the platform's own definitions before a campaign is built, so a filter that would match nobody is rejected with the real alternatives attached.

Tools the agent can call

Before committing to a design, the agent inspects the platform directly. Every tool reads the application's own source, so the answers are current by construction, and they carry the allowed values rather than just the field names — which is what stops the agent guessing a status or a product type. You can watch each call run and open its result.

ToolWhat it answers
list_event_typesWhich events exist, which entity each category's conditions filter, and whether a category is marked new and not yet built.
list_audience_attributesEvery entity and attribute, with its type, the operators it accepts and the exact values it allows.
list_channelsWhich channels this tenant has, in relative cost order, and the delivery statuses each can report.
check_template_availabilityWhether the bank's message template library can be reached.
list_step_typesWhich journey step types the builder supports.
08

The campaign state machine

Every design session moves through explicit states. Transitions are validated. Discovery cannot jump to generation, and a strategy cannot be built without a confirmation recorded for the current brief.

Why confirmations expire

A confirmation is bound to the objective and the strategy version it was given for. If you materially change the objective, the agent restarts discovery and the earlier confirmation stops authorising anything. This prevents a campaign being built for a brief you have since moved on from.

09

Message templates and the bank's library

Communication templates live in the bank's own systems. Hyperface does not mirror them, and we do not want a duplicate catalogue. The agent therefore designs the message without needing the template, and you supply the real identifiers.

The agent provides

The communication objective, draft copy written to the customer, a call to action, personalisation tokens and a recommended channel. All of it is stored on the Send step itself, so it is still there when you open the step to prepare the real message.

You provide

The real account and the real template ID from your own ecosystem, when you prepare the upload. The agent never invents either one, and never implies its draft has been approved.

Three situations are kept distinct, because telling a bank that no suitable template exists when we simply cannot see their library would be false.

StateMeaning
Library unreachableWe cannot confirm or deny that a template exists.
No suitable templateA reachable library was searched and nothing matched.
Awaiting inputPartially supplied. The remaining value is still needed.
10

Validation, export and import readiness

Validation runs against the Drip Campaign platform's own validators. These are the same functions the manual builder uses. Three different things are kept apart, because they are genuinely different: a design that was generated, an artefact that can be exported, and a campaign the target platform would accept.

StateWhat it confirmsTypical result
Design generated The agent produced a journey from the confirmed strategy. Pass
Journey valid Every path connects and terminates. No orphan steps. Pass
Bank details supplied Account and template IDs from your own systems are filled in. Outstanding, and does not block the export
Operational checks Message cap and channel availability are verified against tenant config. Partly unverified
Design exportable The journey is valid and complete as a design, so the JSON can be copied or downloaded. Pass
Import ready Whether the campaign builder would accept this JSON. Unverified — never asserted
Import readiness is unverified, not true and not false

The campaign builder has no JSON import, so there is no import contract to check anything against. The product therefore never claims import readiness. It reports it as unverified and lists what you still have to prepare by hand: the bank's account and template IDs, any campaign field left for a person to decide, and every operational check it could not run. Message spacing, quiet hours and freeze windows are among those. A valid design is not evidence that the platform would accept it.

Blocked means the configuration is wrong, not merely unfinished

A condition naming an attribute the entity does not have, or a value the platform does not define, stops the campaign being generated at all. The real alternatives named. Missing bank IDs are a different thing entirely: they are something only you can supply, so they are tracked for the upload rather than treated as a fault in the design.

The three screens

The Campaign Designer is a standalone application with its own shell and a global tenant selector. It has three screens and no more.

Design

The live campaign canvas on the left and the conversation on the right. The canvas is the real Drip Campaign builder canvas, with the same node cards, edges and node editor.

Knowledge Base

Upload documents the agent should treat as context. Brand guidance, campaign learnings, product rules. Each document is scoped to all tenants or to one.

Run Logs

A readable history of every run. The objective, the context retrieved, each tool call and result, the strategy, the build and the validation outcome.

You can watch the agent work

The response streams as it is written. Alongside it, an activity timeline shows what is actually happening. Context retrieval, each tool request, each tool result with its duration, then graph construction and validation. Once the run finishes the timeline collapses to a single line, so the strategy is what you read.

How the system stays honest

An agent that quietly guesses is worse than no agent. Several rules are enforced in code rather than asked for in a prompt.

Nothing is invented. Not an account, not a template identifier, not a performance figure, not a bank policy.

RuleHow it is enforced
No campaign before confirmation Graph construction has one entry point, guarded by the state machine.
No strategy before discovery A proposal is refused while you have not taken part, success is undefined, or the agent's own dimensions are still open. Enforced in the application, not asked for in the prompt.
An assumption is never a finding A dimension closed on an assumption is recorded as deferred, not retained. A limitation claimed on an assumption is recorded as deferred and marked unverified.
A failed turn loses nothing When a turn fails, the brief and the conversation state come back unchanged, so a retry resumes instead of starting over.
Clarifying does not erase Asking about your own objective withdraws the approval, which you can give again. It never deletes what discovery established.
No invented identifiers Unresolved fields use the platform's own empty value, so its validator rejects them.
No invented capabilities Anything outside the real vocabulary is rejected with a reason rather than corrected.
No unsupported claims There is no performance data, so the agent is instructed never to claim lift or savings.
Synthetic data is labelled Prototype tenants and sample bank context are marked synthetic wherever they appear.
Credentials stay server side The API key is read on the server only. It never reaches the browser bundle or the logs.
No value the platform cannot hold Conditions are checked against the platform's own definitions, and a mismatch is reported with the real alternatives rather than swapped for something similar.
Your words are not rewritten A value you state that the platform cannot represent is raised as a question. The agent does not pick a different attribute on your behalf.
No hidden reasoning exposed The model's private reasoning is passed between its own API calls and nowhere else. It is never shown, never logged and never written to a run record, which hold decisions, durations and results only.
Unbuilt capabilities are flagged Event categories the platform marks as proposed rather than built are raised during the strategy, before anything is generated.
Success is settled first The opening round may ask about the objective and nothing else. That answer decides which other questions are worth asking, so putting them alongside it wastes them.
A factor raised cannot be abandoned A dimension the agent named itself may not reach a proposal unresolved. It must be answered, checked against the platform, or carried as a stated assumption. An assumption with nothing actually assumed counts as unresolved.
A question asked twice falls back A decision-changing question blocks a proposal. Asked twice without an answer, its own stated default applies and the proposal says which, rather than asking a third time. Where no default was given it stays an open decision, not a quiet choice.
Alternatives are really alternatives Two candidate approaches are compared on who they reach, when, and what the journey does. Two descriptions of one campaign are reported as one, whatever they are called.
A test cannot claim more than it can settle An experiment declares what it is able to establish. If its variants run the identical journey it can show which message performs better, and it is refused if it claims to explain why customers behave as they do.
The built campaign is the one described The journey behaviour the agent chose is read back off the campaign actually constructed. A mismatch is reported rather than left for the reader to notice.
What the platform cannot do is stated The agent states the intervention it wants before being told what the builder supports. Anything the platform cannot meet is listed against the proposal in the words of the original request, instead of being narrowed into whatever happened to be buildable.
The reply is written for you Internal identifiers such as question ids, rule codes and raw event names and paths into the data are detected in anything shown to you and sent back to the agent to rewrite. They are never silently stripped, because that changes the meaning rather than the wording.
13

What is not supported yet

This is a working prototype. The following are genuine gaps rather than rough edges, and the product does not pretend otherwise.

  • Tenant context is synthetic. Tenants, channel costs, message caps and quiet hours are sample data. They are not a real bank's configuration.
  • No import path. Campaign JSON is transferred manually. Nothing is saved or activated in the campaign builder.
  • Three operational checks are unverified. Message spacing, quiet hours and freeze windows are reported as unchecked.
  • Document support is limited. Plain text, Markdown, CSV and JSON are read. PDF and Word are refused rather than silently ignored.
  • No analytics engine. Supplied evidence is read as text. There is no query capability and no connection to bank systems.
  • Design quality is judged by a person. The validators prove a campaign is buildable, never that it is a good campaign. A ten-objective evaluation set and a written rubric exist for that, and a human applies them.
  • Suggested copy is unreviewed. No brand check, no compliance check, no channel length limits. It is a starting point for the real message, not an approved one.
  • Live runs are not perfectly reliable. A small share of turns still fail to return a usable answer and have to be retried. The failure is reported plainly rather than hidden behind a generic message, and nothing already established is lost when it happens.
  • Discovery quality is not yet proven end to end. The rules in the previous section are enforced and covered by tests. Whether the resulting conversation reaches the standard we set for it, asking about the business outcome and investigating the audience rather than the plumbing, has not yet been demonstrated in a completed live run.
  • The dimension record can repeat itself. Restating a dimension in different words adds a second entry instead of updating the first, so a long conversation can hold the same question twice. Known, and deliberately not fixed yet.
  • Evidence is self-reported. The agent states whether a status rests on a tool result, on something you said, or on an assumption. Nothing yet cross-checks a claimed tool result against the tools actually consulted.
  • Questions are prose, not choices. A clarifying question cannot yet be offered as a short list of options to pick from.
  • No sight of past campaigns. The agent cannot read campaigns already built, so it cannot reuse an existing segmentation or tell you whether something similar has been tried.
  • Deployment is local. The API runs inside the development server. A hosted deployment would need a server function.

What changed in this round, and why

This round started from a specific complaint. The agent was asked to raise conversion from outstanding balance to EMI, and it spent both of its most valuable questions asking whether it was acceptable to message customers whose KYC might be incomplete, and whether to hold the campaign until a suppression list could be built. Neither question is about EMI conversion.

Two things turned out to be true. The agent had nothing to reason about customers with, which is covered in section 05. And two of the platform limits it described to the user were not real.

ChangeWhy
The agent must establish who converts and why the rest do notIt had asked neither question in thirty-five runs. Both are now required before it can propose anything.
A reason must be traceable to something you saidWithout this, the label saying “the user told me” was just a label the agent applied to its own invention. The quote is now checked against your real replies.
“Nobody knows who converts” now demands more work, not lessIt used to close the question. The agent must now propose at least two candidate segments with its reasoning, wait for your reaction, and build a campaign that can tell them apart.
Every message must name the problem it solvesChecked against the built journey rather than asked for in the prompt.
The platform no longer puts eligibility questions to youOne sentence was responsible. The application used to tell the agent that any unmet requirement was “the user's decision, not yours”. It now separates the two kinds. A gap that changes who gets reached is still yours to decide. A gap in who gets excluded is plumbing, and becomes a stated limitation instead.
Entry can combine several entities, and can require that a record does not existThe agent did not know either was possible, so it described both as limitations to the user. The builder has supported combining entities since October and has always supported checking for absence over a time window. The honest caveat is that absence is measured over a window rather than over all time, and the campaign now says so.

Two problems found in our own checks

Both are worth recording, because in each case something that looked verified was not.

ProblemWhat it meant
The agent server was not being typecheckedA typecheck existed for it but was never run, and the command being used covered only the user interface. The server itself runs in a mode that removes types without checking them. Pointing the checker at it found fifteen errors on the first run. The server is now clean, and the check is part of the build.
A hard constraint was reporting a pass it had not earnedWhen the invented per-campaign message cap was removed, the check that enforced it kept running with no cap to compare against. It recorded a pass for a rule it had never evaluated. A test was holding that behaviour in place. It now correctly reports the rule as unverified.
What this round does not claim

These are changes to what the application requires and refuses. They raise the floor on what can reach you. They do not guarantee that any particular campaign is good. Whether the segments the agent proposes are sensible, and whether its messages are worth sending, is still a judgement you have to make. Every run is recorded in the run log so that judgement can be made from evidence rather than from a description.

Campaign Designer runs as a standalone application alongside the existing Drip Campaign builder. It shares the same campaign model, reducers, canvas and validators, so a generated campaign is the same kind of object as a hand built one.
